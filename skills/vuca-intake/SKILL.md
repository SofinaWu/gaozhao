# VUCA 需求澄清

把一个模糊的招聘需求跑成清晰的、有证据链的人才画像。

> 核心认知：**VUCA 的招聘需求，本质是一个还没被解决的业务问题。**
> 用人方不是懒得写 JD，是他自己还没想清楚。你的交付物不只是人，是**帮他想清楚的过程**。
> 因此：**需求会变是正常的，方向调整是收敛，不是返工。**
>
> 合作底座：先给样本、判断和理解力，不把交付变成「你应该听我的」的隐形账单。与此同时，共创所需的 context、反馈和决策要提前说清；这是明示的工作契约，不是人情债。

## 第 0 步 · 判断是否适用

先读取用户已经提供的阶段、澄清结论和关键未知，能定位下一步就直接处理；只有缺失信息会改变动作时才补问。以下问题和模板按缺口使用，不从第 1 题重问已知条件。

需求已澄清时：条件已定但尚无样本，直接按已确认任务与能力找目标团队、形成带证据和未知的差异化样本，再约用人方反馈；已有样本但标准有分歧，进入第 3 步核对；已有人选在交流或评估，沿对应环节推进。无需为“澄清完了下一步”重跑需求澄清。搭配 `gaozhao` 时，可读其第 1 步模板 7 选择推进动作，再进入寻源、触达或评估步骤。

通常命中两条以上就适合用本 skill（参考值，按具体模糊点判断，不机械凑数），否则走常规 JD 招聘：
- 没有具象 JD，或有 JD 但用人方说「不够到位」
- 没有明确的人才寻访方向
- 新业务，用人部门自己也不熟这个领域
- 用人方说「先都看看，别框死」
- 要解决的问题很多，说不清哪个优先

同时判断是哪一类 VUCA，处理方式不同：

| 类型 | 表现 | 处理 |
|---|---|---|
| 问题复杂/抽象 | 只能说「想解决 XX」 | 从问题反推能力，不从头衔出发 |
| 原因未明或不便明说 | 回避某些追问、强调保密 | 保留未知，不直接断定涉及现有团队；不硬追，按可分享范围了解团队缺口、谁在兼这项工作，再核对解释 |
| 用人方习惯先散后聚 | 主动说「先都看看」 | 顺着走，但必须做记录，否则散完无法收敛 |

## 第 1 步 · 需求沟通（引导用户去问，或陪用户复盘已问到的）

**目标不是拿到画像，是拿到「问题」和「排除条件」。**

### 需求沟通 9 题（按尚未解决的缺口选问）
1. 这个岗位存在，是因为什么问题没被解决？没有这个人，现在谁在扛、扛得怎么样？
2. 他来了之后，在这个岗位正常的见效周期内（常见是三个月左右，按岗位定），哪件**具体的事**会变得不一样？（不要「提升效率」这种）
3. 为什么是现在招？为什么不是半年前 / 半年后？
4. 向谁汇报？和谁抢资源？
5. **哪些人是明显不合适的？**（尽量多问几条，建议三条左右，但不为凑数制造筛选条件 —— 这题的答案通常比「要什么样的人」清晰十倍）
6. 如果只能满足一条要求，你保哪条？
7. 上一个做类似事的人为什么没成 / 为什么走了？
8. 需要他自己动手落地，还是只出策略？（尚未明确且会影响画像时补问；已确认的不重复询问）
9. 价值观校准：对同一件事的归因思路，哪些底层理念需要一致？（落到具体问题上校准；视角和结论可以不同，不要求分析结论一律相同）

### 同时记录潜台词（明说 / 推断分开写）
- 反复强调的软性词（「聪明」「靠谱」「胆子大」）→ 请其提供具体行为和业务原因，形成候选解释后交回确认，不替他定义后直接作为标准
- 对某类背景反应特别快（正或负）→ 记录偏好，核对其经历与依据，不直接断定原因
- 说「都可以看看」但只对某一类给正反馈 → 保留原话与实际选择之间的差异，用对照样本检验，不直接选一边当事实
- 回避追问 → 记为未知，保留其他解释，按需要寻找可用旁证

## 第 3 步 · 用样本换需求（最关键的动作）

抽象追问「你到底要什么样的人」得不到答案。**给他具体的人去反应。**

1. 按问题而非头衔，列不同方向的人才假设，例如从研发、商业化、数据侧解决问题；可参考 3–4 个方向，不为凑数制造方向。
2. 各找少量有差异的具体样本，公开信息即可，不必已经接触；可参考每方向 3–5 人，优先保证可比较性。
3. 请用人方排序并说明赞同、反对的理由，记录原话。理由首先说明当前关注或偏好，不自动证明岗位必须具备某个条件。
4. 将反馈与岗位任务对照：缺少该条件会影响什么？是否有其他解释？背景不同但做成同类任务的人能否提供同等证据？分别归为硬门槛、属性、背景偏好或待验证。
5. 先写入反馈记录，选一个追问、对照样本或旁证验证。确需改变方向或要求时，带业务依据请相关拍板人确认，再更新澄清表版本；不能把一次口头偏好直接升级为过滤条件。

例：“大厂背景更靠谱”先记为背景偏好或待验证。核对其担心的是交付规模、协作复杂度还是其他问题，再比较不同背景但任务证据相当的样本；未验证前不筛掉非大厂人选。

## 第 4 步 · 常态运转

| 频率 | 动作 |
|---|---|
| 每周（建议节奏） | 按当前阶段提供可比较样本或安排相关人选交流，节奏按岗位和决策人时间调整；以有依据的反馈推进收敛，信息不再增加时回查条件，不只靠增加人数 |
| 每轮寻源后 | 先提取关键信息，再写三段式：Deliverables 关键交付 / Findings 核心发现 / Conclusions 推进结论 |
| 方向或要求调整时 | 核对业务依据，取得相关拍板人确认后升版，保留旧版；只新增反馈不自动升版 |
| 每轮面试后 | 对照通过与未通过样本及后续表现，记录支持与反例；新解释先待验证，要求变化走确认流程 |

## 心态基线（对新手最重要的一段）

- **没有 ddl、一切未知，一开始一定会焦虑**——这是这类需求的固有属性，不是你能力不足
- **胆子大一点，去繁为简**，在动态过程中摸方向。要求自己一开始就找到正确方向 = 卡死
- **不懂就问，不怕犯错**。暴露自己的不懂是一种**交底行为**，是建立信任的关键，不是丢脸
- **主动表达，先打开自己**。等着对方把需求说清楚再动，永远等不到

## 失败模式（自查）

| 失败模式 | 修正 |
|---|---|
| 等需求清楚了再动 | 先给样本，用样本换需求 |
| 把方向调整当返工 | 前几轮的 findings 就是资产 |
| 只记结论不记过程 | 三段式 + 澄清表版本号 |
| 忽略原话与实际反馈之间的差异 | 并列记录，用任务与对照样本验证解释，不把任何一次偏好直接写成门槛 |
| 澄清做成审问 | 姿态是「一起解题」，不是「你说清楚我才干」 |
| 把交付变成人情筹码 | 样本和 findings 用于换信息，不用于换服从；协作条件提前明示 |
| 需求方不愿参与还硬做 | 见下 |

## 何时该拒接 / 明确边界

需求方**不愿意一起想清楚**（不给时间、不给反馈、不接受方向调整、只重复「你按 JD 找就行」）
→ 这不是 VUCA 需求，这是无底洞。明确说出边界。

## 环境依赖（外部客户场景必读）

本方法的高效运转依赖能拿到**充分真实的一手 context**（透明的沟通环境、决策人日志、项目信息）。
不具备时的降级路径：
- 拿不到一手 context → 用**公开产出**反推：这家公司近半年发了什么、招了什么人、组织变了什么
- 拿不到决策人时间 → 可改用带差异化样本的书面对比材料换取反馈；频率和样本数按关键未知与对方时间约定，不另设固定周数或人数门槛
- 拿不到内部旁证 → 从**离职者与外部合作方**取证
